## 1. Levin framing

Every message is a 33-byte header followed by a body. The body is an
**epee portable storage** blob ([04 §2](04-serialization.md)).

```
offset size  field
  0     8    signature      = 01 21 01 01 01 01 01 01   (bytes, as sent)
  8     8    length         u64 LE, body length, header NOT included
 16     1    expect_response  0 = no, non-zero = yes
 17     4    command        u32 LE
 21     4    return_code    i32 LE (0 in requests)
 25     4    flags          u32 LE  (bit0 Q, bit1 S, bit2 B, bit3 E)
 29     4    version        u32 LE = 1
```

The signature is the little-endian encoding of two u32s `0x01011101` and
`0x01010101` — on the wire the 8 bytes are
`01 21 01 01 01 01 01 01` as documented in `docs/LEVIN_PROTOCOL.md`. Copy the
byte sequence, do not re-derive it.

Flags:

| Bit | Name | Meaning |
|---|---|---|
| 0 | `Q` | request |
| 1 | `S` | response |
| 2 | `B` | beginning of a fragmented message |
| 3 | `E` | end of a fragmented message |

Message kinds:

| Kind | Q | S | B | E | expect_response |
|---|---|---|---|---|---|
| Notification | 1 | 0 | 0 | 0 | 0 |
| Request | 1 | 0 | 0 | 0 | ≠ 0 |
| Response | 0 | 1 | 0 | 0 | 0 |
| Fragment (first) | 0 | 0 | 1 | 0 | 0 |
| Fragment (middle) | 0 | 0 | 0 | 0 | 0 |
| Fragment (last) | 0 | 0 | 0 | 1 | 0 |
| Dummy | 0 | 0 | 1 | 1 | 0 |

- Responses MUST be sent in the order the requests arrived (other messages may be
  interleaved between them).
- Reassembled fragments contain a **complete nested Levin header** for the real
  message.
- Dummy messages MUST be accepted and discarded.
- Reject messages whose `length` exceeds the configured maximum. The reference
  uses **two** limits (`contrib/epee/include/net/levin_base.h`):
  `LEVIN_INITIAL_MAX_PACKET_SIZE = 256 KiB` **before** the handshake completes and
  `LEVIN_DEFAULT_MAX_PACKET_SIZE = 100_000_000` after. Apply both — the
  pre-handshake limit is what stops an unauthenticated peer from making you
  allocate 100 MB. `P2P_DEFAULT_PACKET_MAX_SIZE (50_000_000)` is the separate
  advertised `network_config` value.

The header is `epee::levin::bucket_head2`, `#pragma pack`ed:
`u64 m_signature, u64 m_cb, u8 m_have_to_return_data, u32 m_command,
i32 m_return_code, u32 m_flags, u32 m_protocol_version` = 33 bytes. Flag
constants are `LEVIN_PACKET_REQUEST 0x1`, `RESPONSE 0x2`, `BEGIN 0x4`, `END 0x8`;
`m_protocol_version` is `LEVIN_PROTOCOL_VER_1 = 1`.

## 2. Command set

| ID | Name | Kind |
|---|---|---|
| 1001 | `COMMAND_HANDSHAKE` | request/response |
| 1002 | `COMMAND_TIMED_SYNC` | request/response |
| 1003 | `COMMAND_PING` | request/response |
| 1007 | `COMMAND_REQUEST_SUPPORT_FLAGS` | request/response |
| 2001 | `NOTIFY_NEW_BLOCK` | notification |
| 2002 | `NOTIFY_NEW_TRANSACTIONS` | notification |
| 2003 | `NOTIFY_REQUEST_GET_OBJECTS` | notification |
| 2004 | `NOTIFY_RESPONSE_GET_OBJECTS` | notification |
| 2006 | `NOTIFY_REQUEST_CHAIN` | notification |
| 2007 | `NOTIFY_RESPONSE_CHAIN_ENTRY` | notification |
| 2008 | `NOTIFY_NEW_FLUFFY_BLOCK` | notification |
| 2009 | `NOTIFY_REQUEST_FLUFFY_MISSING_TX` | notification |
| 2010 | `NOTIFY_GET_TXPOOL_COMPLEMENT` | notification |

IDs 1004–1006 (`STAT_INFO`, `NETWORK_STATE`, `PEER_ID`) and 2005 are historical
and not implemented by the reference node. A Rust node MUST NOT send them and
SHOULD return `LEVIN_ERROR_CONNECTION_HANDLER_NOT_DEFINED` if asked.

Note 2003/2004 and 2006/2007 are **notifications**, not request/response pairs,
despite being logically paired — so responses can arrive in any order and a peer
may never answer.

## 3. Common structures

Field names below are the exact portable-storage / JSON entry names.

### 3.1 `network_address`

A nested section:

```
type : u8      # 1 = ipv4, 2 = ipv6, 3 = i2p, 4 = tor (0 = invalid)
addr : object  # type-dependent
```

For `ipv4` the `addr` section is:

```
m_ip   : u32   # the 4 bytes on the wire, in wire order, are the octets a.b.c.d
m_port : u16   # the port number
```

For `ipv6`: `addr : { addr : string(16 bytes), m_port : u16 }`.
Tor/i2p carry a host string and port. An unsupported `type` is an **error** in
the reference (`MERROR ... return false`), so a Rust node must at minimum parse
types 1–4 structurally even if it cannot connect to 3/4.

### 3.2 `peerlist_entry`

```
adr                  : network_address
id                   : u64        # peer id
last_seen            : i64  OPT default 0
pruning_seed         : u32  OPT default 0
rpc_port             : u16  OPT default 0
rpc_credits_per_hash : u32  OPT default 0
```

### 3.3 `basic_node_data`

```
network_id           : string (16 bytes, POD_AS_BLOB)
peer_id              : u64
my_port              : u32        # 0 means "do not add me to peer lists"
rpc_port             : u16  OPT default 0
rpc_credits_per_hash : u32  OPT default 0
support_flags        : u32  OPT default 0
```

### 3.4 `CORE_SYNC_DATA`

```
current_height              : u64
cumulative_difficulty       : u64        # low 64 bits
cumulative_difficulty_top64 : u64  OPT default 0 (always written)
top_id                      : string (32 bytes, POD_AS_BLOB)
top_version                 : u8   OPT default 0
pruning_seed                : u32  OPT default 0
```

`top_version` is `get_ideal_hard_fork_version(current_height)`.

### 3.5 `block_complete_entry`

```
pruned       : bool OPT default false
block        : string      # the full block blob
block_weight : u64  OPT default 0
txs          : depends on `pruned`:
                 pruned == true  -> array of objects
                                    { blob: string, prunable_hash: string(32) }
                 pruned == false -> array of strings (raw tx blobs)
```

The `pruned` flag changes the **type** of the `txs` entry. A reader must check
`pruned` first.

## 4. Handshake

### 4.1 Flow

```
A -> B  COMMAND_HANDSHAKE request  { node_data, payload_data }
B -> A  COMMAND_HANDSHAKE response { node_data, payload_data, local_peerlist_new }
```

Response body:

```
node_data          : basic_node_data
payload_data       : CORE_SYNC_DATA
local_peerlist_new : array of peerlist_entry   # up to P2P_DEFAULT_PEERS_IN_HANDSHAKE (250)
```

### 4.2 Acceptance rules

The responder MUST drop the connection if:

- `node_data.network_id != NETWORK_ID` → "wrong network" (this is the fork guard).
- `node_data.peer_id == my_peer_id` → self-connection.
- The peer is banned.
- More than `P2P_MAX_PEERS_IN_HANDSHAKE (250)` peerlist entries are returned.

After a successful handshake:

- If `node_data.my_port != 0` and the connection is incoming, the responder
  attempts a **ping-back** (`COMMAND_PING` on a fresh connection to
  `remote_ip:my_port`) and only adds the peer to its white list if the ping
  returns `status == "OK"` with the matching `peer_id`. This is the only way a
  peer enters the white list.
- `support_flags` is requested separately with `COMMAND_REQUEST_SUPPORT_FLAGS` if
  the handshake reported none.
- `process_payload_sync_data` is called; see §5.

### 4.3 Version-mismatch warning

`cryptonote_protocol_handler.inl` around line 445:

```
if version >= 6 && version != hshd.top_version:
    if version < hshd.top_version && version == get_ideal_hard_fork_version():
        log a prominent "you need to update" warning
```

Informational only; the connection is kept. Reproducing the warning is optional,
but a Rust node MUST NOT drop peers over a `top_version` mismatch.

### 4.4 Timed sync

Every `P2P_DEFAULT_HANDSHAKE_INTERVAL (60 s)` per connection:

```
A -> B  COMMAND_TIMED_SYNC request  { payload_data: CORE_SYNC_DATA }
B -> A  COMMAND_TIMED_SYNC response { payload_data, local_peerlist_new }
```

Used to learn of new tips and to exchange peers. A connection that does not
answer within `P2P_DEFAULT_INVOKE_TIMEOUT (2 min)` is dropped.

## 5. Chain synchronisation

### 5.1 Deciding to sync

`process_payload_sync_data(hshd, context, is_initial)`:

- If `hshd.current_height == 0` → drop (peer has no chain).
- Compare `(cumulative_difficulty_top64, cumulative_difficulty)` as a `u128`
  against the local value. If the peer is ahead → enter
  `state_synchronizing` and request the chain.
- If the peer's `top_id` is a block we already have and its height is lower →
  the peer is behind; note it and possibly drop after a grace period.
- Track `context.m_remote_blockchain_height` and `m_pruning_seed`.

### 5.2 `NOTIFY_REQUEST_CHAIN` (2006)

```
block_ids : string    # CONTAINER_POD_AS_BLOB: 32*n concatenated block hashes
prune     : bool OPT default false
```

`block_ids` is a **sparse chain** built by `get_short_chain_history()`: the most
recent 10 block ids sequentially, then with exponentially increasing gaps
(2, 4, 8, 16, …), and **always the genesis hash last**.

### 5.3 `NOTIFY_RESPONSE_CHAIN_ENTRY` (2007)

```
start_height                : u64
total_height                : u64
cumulative_difficulty       : u64
cumulative_difficulty_top64 : u64  (always written)
m_block_ids                 : string  (32*n, CONTAINER_POD_AS_BLOB)
m_block_weights             : string  (8*n u64 LE, CONTAINER_POD_AS_BLOB)
first_block                 : string  # the blob of the block at start_height
```

The responder finds the most recent id from the request that it has, and returns
up to `BLOCKS_IDS_SYNCHRONIZING_DEFAULT_COUNT (10_000)` ids from there. The
requester MUST verify that `m_block_ids[0]` is a block it has (the split point).

Reject a response with more than `BLOCKS_IDS_SYNCHRONIZING_MAX_COUNT (25_000)`
ids.

### 5.4 `NOTIFY_REQUEST_GET_OBJECTS` (2003)

```
blocks : string   # 32*n block hashes (CONTAINER_POD_AS_BLOB)
prune  : bool OPT default false
```

Request at most `BLOCKS_SYNCHRONIZING_MAX_COUNT (2048)` blocks.
**Align requests to `SEEDHASH_EPOCH_BLOCKS` (2048) boundaries** so that a batch
shares one RandomWOW seed ([03 §3.4](03-pow.md)).

### 5.5 `NOTIFY_RESPONSE_GET_OBJECTS` (2004)

```
blocks                    : array of block_complete_entry
missed_ids                : string (32*n, CONTAINER_POD_AS_BLOB)
current_blockchain_height : u64
```

The requester MUST verify that every returned block was requested and that the
transactions match the block's `tx_hashes` (in order, by hash). A mismatch is a
protocol violation → drop and ban the peer.

### 5.6 Span queue

The reference maintains a `block_queue` of in-flight *spans* across peers,
assigning each peer a contiguous height range and reordering completed spans for
in-order application. A Rust implementation SHOULD do the same; a simple
one-peer-at-a-time sync is acceptable for M2 but will be slow.

Sizing: `BLOCKS_SYNCHRONIZING_DEFAULT_COUNT (20)` blocks per request by default,
growing adaptively toward `BLOCKS_SYNCHRONIZING_MAX_COUNT`.

## 6. Block propagation

### 6.1 Fluffy blocks

`NOTIFY_NEW_FLUFFY_BLOCK` (2008) is the default (`P2P_SUPPORT_FLAG_FLUFFY_BLOCKS`
is always set):

```
b                         : block_complete_entry   # txs contains ONLY txs the peer may lack
current_blockchain_height : u64
```

The receiver fills missing transactions from its own mempool. If any are still
missing it sends:

`NOTIFY_REQUEST_FLUFFY_MISSING_TX` (2009):

```
block_hash                : string(32)
current_blockchain_height : u64
missing_tx_indices        : string (8*n u64 LE, CONTAINER_POD_AS_BLOB)
```

and the peer replies with a full `NOTIFY_NEW_FLUFFY_BLOCK` containing those
transactions.

### 6.2 Full blocks

`NOTIFY_NEW_BLOCK` (2001) carries the block with all its transactions. Sent only
to peers that did not advertise `P2P_SUPPORT_FLAG_FLUFFY_BLOCKS`. A Rust node
MUST accept it and SHOULD prefer sending fluffy blocks.

### 6.3 Mempool complement

`NOTIFY_GET_TXPOOL_COMPLEMENT` (2010):

```
hashes : string (32*n, CONTAINER_POD_AS_BLOB)
```

"Here are the tx hashes I have; send me anything else in your pool." The
responder replies with a `NOTIFY_NEW_TRANSACTIONS` containing the difference.
Sent after a fluffy block to catch up the pool.

## 7. Transaction relay — Dandelion++

`src/cryptonote_protocol/levin_notify.cpp`, `src/cryptonote_core/tx_pool.cpp`.

### 7.1 `NOTIFY_NEW_TRANSACTIONS` (2002)

```
txs               : array of string        # raw tx blobs
_                 : string                 # padding, may be empty
dandelionpp_fluff : bool OPT default TRUE  # note the default!
```

The `_` field exists to pad messages to a uniform size for traffic analysis
resistance. The `OPT default true` means a peer that omits the flag is treated as
sending in **fluff** mode — backwards compatibility with pre-Dandelion nodes.

### 7.2 Epochs and stems

- Every `CRYPTONOTE_DANDELIONPP_MIN_EPOCH (10 min)` plus a random
  `[0, CRYPTONOTE_DANDELIONPP_EPOCH_RANGE (30 s))`, a new epoch begins.
- Per epoch, choose `CRYPTONOTE_DANDELIONPP_STEMS (2)` outgoing connections as
  **stem peers**, and a stable mapping from each incoming peer to one stem peer.
- A newly received stem transaction is forwarded to its mapped stem peer with
  probability `100 - CRYPTONOTE_DANDELIONPP_FLUFF_PROBABILITY` = 80%; otherwise
  it is **fluffed** (broadcast to all peers).
- Each stem transaction gets an **embargo timer**, exponentially distributed with
  mean `CRYPTONOTE_DANDELIONPP_EMBARGO_AVERAGE (39 s)`. If the transaction has
  not been seen in fluff mode by the time the embargo expires, fluff it.
- Fluff-mode flushes are batched on a Poisson timer with mean
  `CRYPTONOTE_DANDELIONPP_FLUSH_AVERAGE (5 s)`.
- Locally originated transactions always start in stem mode.

### 7.3 Relay method

`tx_pool` tracks a per-transaction `relay_method`:

| Method | Meaning |
|---|---|
| `none` | do not relay |
| `local` | originated here, not yet relayed |
| `forward` | received over i2p/tor, to be forwarded with delay |
| `stem` | Dandelion++ stem phase |
| `fluff` | broadcast |
| `block` | came in a block |

`do_not_relay` in `send_raw_transaction` maps to `none`.

### 7.4 Noise / covert send (optional)

For i2p/tor zones the node maintains `CRYPTONOTE_NOISE_CHANNELS (2)` channels
emitting `CRYPTONOTE_NOISE_BYTES (3 KiB)` every
`CRYPTONOTE_NOISE_MIN_DELAY (10 s)` + `[0, 5 s)`, using Levin fragmentation to
hide real transactions among dummy messages (`CRYPTONOTE_MAX_FRAGMENTS = 20`).
Out of scope for the first release; the **fragment and dummy message handling in
§1 is not optional**, because a peer may send them.

## 8. Peer management

### 8.1 Peer lists

- **White list** — peers we have successfully connected to *and* ping-backed.
  Capacity `P2P_LOCAL_WHITE_PEERLIST_LIMIT (1000)`.
- **Gray list** — peers we learned about but have not verified. Capacity
  `P2P_LOCAL_GRAY_PEERLIST_LIMIT (5000)`.
- **Anchor list** — peers we had a long-lived outgoing connection to; on startup
  the node connects to `P2P_DEFAULT_ANCHOR_CONNECTIONS_COUNT (2)` of them first,
  as an eclipse-attack mitigation.

Outgoing connection selection: `P2P_DEFAULT_WHITELIST_CONNECTIONS_PERCENT (70)`
of attempts target the white list, the rest the gray list. Target
`P2P_DEFAULT_CONNECTIONS_COUNT (12)` outgoing connections.

Persisted to `p2pstate.bin` in **epee portable storage** with a version tag. A
Rust node MAY use its own format (the file is local, not consensus) but SHOULD
then use a different filename to avoid confusing a C++ node sharing the data dir.

### 8.2 Bans

- `P2P_IP_FAILS_BEFORE_BLOCK (10)` failures within
  `P2P_FAILED_ADDR_FORGET_SECONDS (3600)` → ban for
  `P2P_IP_BLOCKTIME (86400 s)`.
- Explicit bans via the `set_bans` RPC.
- `--ban-list <file>` loads a static list.
- DNS blocklist support (`DNS_BLOCKLIST_LIFETIME`) — optional.
- Protocol violations (bad PoW, malformed messages, unrequested objects) ban
  immediately. A transaction rejected for a **policy** reason sets
  `no_drop_offense` and MUST NOT ban.

### 8.3 Connection lifecycle

- Handshake timeout `P2P_DEFAULT_HANDSHAKE_INVOKE_TIMEOUT (5 s)`.
- Connect timeout `P2P_DEFAULT_CONNECTION_TIMEOUT (5 s)`.
- Idle connections killed after `P2P_IDLE_CONNECTION_KILL_INTERVAL (300 s)`.
- Rate limits default to `P2P_DEFAULT_LIMIT_RATE_UP (8192 kB/s)` /
  `_DOWN (32768 kB/s)`; adjustable at runtime via the `set_limit` RPC.

### 8.4 Seeding

On first start (empty peer lists) the node connects to the hard-coded seed list
([01 §12.2](01-constants.md#122-seed-nodes-mainnet)), picking one at random.
**There are no DNS seeds.** If all seeds are unreachable the node cannot
bootstrap; `--add-peer` / `--seed-node` are the manual escape hatches.

## 9. Pruning (optional)

`pruning_seed` is a `u32` encoding a stripe (1..8) and log-stripes (3):
`CRYPTONOTE_PRUNING_LOG_STRIPES = 3`, `CRYPTONOTE_PRUNING_STRIPE_SIZE = 4096`,
`CRYPTONOTE_PRUNING_TIP_BLOCKS = 5500`. A pruned peer only stores the prunable
part of transactions for blocks in its stripe.

A non-pruning node advertises `pruning_seed = 0`, MUST parse the field from
peers, and MUST NOT request pruned blocks that it intends to fully verify.

## 10. Conformance checklist

- [ ] Levin header is 33 bytes with the exact signature byte sequence.
- [ ] Fragmented and dummy messages are handled.
- [ ] `network_id` mismatch drops the connection — this is the fork guard.
- [ ] Self-connection (matching `peer_id`) is detected and dropped.
- [ ] `top_version` mismatch does **not** drop the peer.
- [ ] `NOTIFY_NEW_TRANSACTIONS.dandelionpp_fluff` defaults to **true** when absent.
- [ ] `block_complete_entry.txs` type switches on `pruned`.
- [ ] `CONTAINER_POD_AS_BLOB` fields are parsed as one concatenated string with a
      length that is a multiple of the element size.
- [ ] Block requests are capped at 2048 and aligned to 2048-block boundaries.
- [ ] Returned blocks are checked against what was requested, and their
      transactions against `tx_hashes`.
- [ ] Only ping-backed peers enter the white list.
- [ ] Policy-rejected transactions set `no_drop_offense` and do not ban.
- [ ] Commands 1004–1006 and 2005 are neither sent nor required.
